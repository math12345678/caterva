# Caterva runtime dependencies.
# Pinned to versions verified working together on 2026-07-22.
#
# Python 3.10-3.13 is required.
#
# The reason, verified against PyPI 2026-08-02 -- an earlier version of this
# comment named the wrong cause:
#
#   libroadrunner 2.8.0   cp310-cp313          covers the full window
#   numpy         2.2.6   cp310-cp313          covers the full window
#   python-libsbml 5.21.1 cp38-cp314          NOT a blocker
#   antimony      2.14.0  py3-none-<platform> NOT a blocker (version-agnostic)
#
# So it is NOT "the SBML C extensions stop at cp312", which this file, the
# README and CONTRIBUTING.md all claimed. python-libsbml already ships cp314
# wheels, and antimony's wheels are Python-version agnostic.
#
# 3.13 support landed via the NumPy 2.x upgrade (ADR 0014): libroadrunner is
# on the 2.8.0 line and numpy on 2.2.x -- the first lines that publish cp313
# wheels while still covering the cp310 floor. numpy must stay on 2.2.x:
# libroadrunner 2.8.0 pins numpy~=2.2, and numpy 2.2.x is the last line that
# also satisfies both scipy pins' numpy caps (1.15.3 <2.5, 1.16.0 <2.6) with a
# single pin for every supported interpreter. See
# docs/adr/0014-python-version-support.md.

# --- Simulation engines (Tier 2 ODE domains) -------------------------------
# NOTE: do NOT `pip install tellurium`. The umbrella package pulls in
# python-libcombine and python-libnuml, which are only needed for COMBINE
# archives and numerical markup -- neither of which Caterva uses. On any
# platform without prebuilt wheels for them, that install fails at the cmake
# step. These three packages are the parts that actually do the work.
#
# libroadrunner is pinned to 2.8.0 because it is the only release line that
# still ships cp310 wheels while adding cp313 (verified against PyPI). The
# 2.9.x line dropped cp310 wheels entirely (releases start at cp311), which
# would break the Python 3.10 floor -- the exact failure that 2.9.0 caused
# in CI ("No matching distribution found for libroadrunner==2.9.0").
libroadrunner==2.8.0
antimony==2.14.0
python-libsbml==5.21.1
# SED-ML, for the COMBINE archive export. BSD (Frank Bergmann, Heidelberg),
# so it sits under Apache-2.0 without the separation stdpopsim needed --
# see docs/LICENSING.md for the GPL case (and, since 2026-11-01,
# archive/legacy_domains/requirements-popgen.txt for the file it was).
#
# A hard dependency rather than optional: the archive is built THROUGH
# libSEDML rather than string-formatted, so the document is correct by
# construction and validated before it is written. Hand-writing the XML
# would remove the dependency and replace it with an unverifiable claim
# that the output is valid SED-ML.
python-libsedml==2.0.33

# --- Numerics --------------------------------------------------------------
numpy==2.2.6
# scipy is split by interpreter. 1.15.3's cp313 arm64 wheel does not load on
# macOS 27.0.1: `import scipy.sparse.linalg` -- and with it
# scipy.optimize -- fails in dlopen with "section '__DATA/__thread_bss' has a
# zero-fill section type, but offset field is not zero", so steady-state
# analysis and influence ranking stopped working. 1.15.2 fails the same way;
# 1.16.0 is the first release after 1.15.3 that imports there (checked
# 2026-10-31, each of 1.16.0-1.18.0 tried). 1.16.0 requires Python >=3.11, so
# 3.10 keeps 1.15.3
# -- the last line with cp310 wheels; whether its cp310 wheel shows the same
# macOS 27 failure is unchecked (no 3.10 interpreter was available).
scipy==1.15.3; python_version < "3.11"
scipy==1.16.0; python_version >= "3.11"

# --- Population genetics -----------------------------------------------
#
# stdpopsim MOVED to requirements-popgen.txt on 2026-08-16 (ADR 0061 is
# dated 2026-08-15; the commit, b1bc8f4, is 2026-08-16). It is NOT
# installed by default, and that is a licence decision rather than a
# packaging preference.
#
# stdpopsim is GPL-3.0-or-later. Caterva is Apache-2.0. Those licences are
# compatible in one direction only: Apache-2.0 code may be taken into a
# GPLv3 work, but GPLv3 code cannot be folded into a work distributed under
# Apache-2.0 without the combination becoming GPLv3. Listing it here made
# `make setup` place GPL code into the default environment of a project that
# declares Apache-2.0 — a tension a reader would have had to discover by
# reading two licence files and inferring the interaction.
#
# The code had always treated it as optional. `Tests/popgen_resolver.py`
# wrapped `import stdpopsim` in try/except ImportError and returned
# `found=False` with a search log saying so; the 19 popgen tests skipped
# cleanly and `make check` reported the absence as a warning. So the
# manifest was the only place claiming it was required, and it was the only
# place that was wrong.
#
# 2026-11-01: the resolver, its tests and requirements-popgen.txt moved to
# archive/legacy_domains/ (v0.6.0 is the last release that ships them), so
# no live manifest installs stdpopsim and nothing live imports it. This
# section used to end "To use the population-genetics resolver: pip
# install -r requirements-popgen.txt"; check out v0.6.0 for that instead.
#
# See NOTICE, "Third-party software", and
# docs/adr/0061-gpl-out-of-the-default-install.md.
