# ADR 0008: Parameter Provenance Tracking

**Date:** August 2026  
**Status:** Accepted  
**Stakeholders:** Science team, Auditing, Literature verification

## Problem

A simulation result is only useful if you know where each parameter value came from:

- **User-supplied:** "I explicitly said beta=0.5"
- **Literature-derived:** "Extracted from Kermack & McKendrick 1927"
- **LLM-guessed:** "The language model guessed this, but we haven't verified it"
- **Default:** "We picked this standard value"

Without provenance, users can't judge parameter reliability, and auditors can't verify scientific claims.

## Solution

**Every parameter carries provenance metadata.**

Each parameter in the response has a `ParameterProvenance` object:

```typescript
interface ParameterProvenance {
  origin: "resolved" | "user" | "llm" | "default";
  source?: string;           // What looked it up (e.g., "BRENDA enzyme database")
  citation?: string;         // Formatted citation string
  organism?: string;         // Organism this was measured from
  citationStatus?: "verified" | "flagged";  // Cross-species match?
  assayConditions?: {...};   // pH, temperature, etc.
  strendaStatus?: "complete" | "incomplete";  // STRENDA compliance
  citationLocators?: [{kind, value, deepLink}];  // Machine-checkable refs
  note?: string;             // If lookup failed, why
}
```

## Four Origins

### 1. **resolved** — Literature lookup succeeded

```json
{
  "origin": "resolved",
  "source": "BRENDA enzyme database",
  "citation": "Kermack, McKendrick (1927) Royal Society 115:700-721",
  "organism": "Homo sapiens",
  "citationStatus": "verified",
  "strendaStatus": "complete",
  "citationLocators": [
    {"kind": "pubmed", "value": "12345678", "deepLink": "..."}
  ]
}
```

### 2. **user** — User supplied it explicitly

```json
{
  "origin": "user",
  "note": "Supplied in query: km=5"
}
```

User-supplied values are trusted—users are responsible for correctness.

### 3. **llm** — Language model guessed it

```json
{
  "origin": "llm",
  "note": "LLM suggested beta=0.3 for measles transmission. No literature corroboration."
}
```

LLM guesses are flagged as unverified. They're served but the user sees the warning.

### 4. **default** — Project standard value

```json
{
  "origin": "default",
  "source": "Terrium standard parameters",
  "note": "Lotka-Volterra default: alpha=0.5 (Lotka 1925, Volterra 1926)"
}
```

Defaults are documented with their own literature backing.

## Critical Design Decisions

### Decision 1: No "origin: resolved" without citation

**Rule:** If `origin === "resolved"`, there MUST be a citation.

**Why:** The whole point of tracking origin is to know what we're claiming. An unsubstantiated "resolved" is a lie.

**Enforcement:** `validateParameterProvenance()` in `provenance.ts` throws if this is violated.

### Decision 2: LLM guesses are distinct from defaults

**LLM case:**
```json
{"origin": "llm", "note": "LLM suggested..."}
```

**Default case:**
```json
{"origin": "default", "source": "Terrium...", "citation": "..."}
```

**Why:** Defaults are vetted project choices with scientific backing. LLM guesses are speculative. Users need to know the difference.

### Decision 3: Per-parameter provenance is required, not optional

**Rule:** Every parameter in the response must have a provenance entry.

**Why:** A missing entry is indistinguishable from an unknown origin, which is scientifically unacceptable.

**Enforcement:** 
- At computation time: `queryResolver` throws `RequiredParametersMissingError` if a required parameter has no known origin (ADR 0008 decision #3)
- At serialization time: `guardSerializationProvenance()` verifies every parameter has an entry before the response leaves the API

### Decision 4: STRENDA compliance is separate from origin

STRENDA (Minimum Information About A Protein Assay) requires reporting assay conditions (pH, temperature, etc.) for kinetic measurements.

```json
{
  "origin": "resolved",
  "strendaStatus": "complete",  // or "incomplete"
  "assayConditions": {
    "pH": 7.4,
    "temperature_celsius": 37
  }
}
```

Incomplete STRENDA is flagged but doesn't block the result (it's a soft warning).

## Verification Layers

Provenance is verified at multiple points:

### 1. Computation time (queryResolver.ts)
- If LLM returns a parameter: tag it `origin: "llm"`
- If literature lookup succeeds: tag it `origin: "resolved"` + citation
- If user supplied it: tag it `origin: "user"`
- If neither: throw `RequiredParametersMissingError`

### 2. Engine time (simulate.ts)
- Engine may return auto-generated parameters (e.g., seed)
- Tag these `origin: "default"` with honest note: "Auto-generated by engine for reproducibility"

### 3. Serialization time (simulate.ts → guardSerializationProvenance)
- Before sending to client, verify all parameters have provenance entries
- Flag any missing entries as violations
- Serve with flag if found (degraded-but-real per error handling philosophy)

### 4. Cache time (simulate.ts → cachedProvenance)
- Database cache path doesn't recompute provenance
- Reads it from what was saved
- Must validate on read to catch any pre-migration data

## Usage for API Consumers

Users should check `parameterProvenance` in the response:

```javascript
response.parameterProvenance.beta  // or any parameter
// {
//   origin: "resolved",
//   citation: "Kermack, McKendrick (1927) Royal Society...",
//   citationStatus: "verified"
// }
```

A value with `origin: "llm"` should be treated as speculative and verified independently.

A value with `origin: "user"` is trusted as-is—the user supplied it.

A value with `origin: "default"` is the project's recommendation, backed by literature.
