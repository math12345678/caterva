# Caterva v0.6.0

**A model's numbers carry their evidence, and a second program can re-check
them.** With `--claims DIR`, `caterva compose` keeps the BRENDA pages its
constants came from, `caterva why` prints a claim down to those bytes and
`caterva verify` re-checks them offline. Caterva Studio shows each number's
derivation, re-checks a run, fits your own rates and has an assistant that
is off until you turn it on. The search itself is as in 0.5.1: it reads
BRENDA live, and nothing in Caterva serves a recorded page as the current
one. The notes for 0.5.0 and 0.5.1 still describe the other screens and
commands.

## Claims: `--claims DIR`

```
caterva compose "Michaelis Menten" --subject 2.7.1.1 --organism human --substrate glucose --claims ./claims
```

- **What it writes.** A directory: every BRENDA page the resolver read, as
  the bytes it read them (gzipped, named by their sha256), BRENDA's
  literature page for each cited reference, the rows taken from the pages,
  and one claim per constant: cited (a row, with byte spans in the page for
  the row's reference id, value, commentary, substrate and organism), chosen
  (a starting amount you set), placeholder (the table that would have
  supplied it, and did not), refused (no row on the pinned page matched what
  the resolver reported; the candidates are named, and no citation is
  given), and one computed claim for the model, over all of them. The
  report's last section, before the footer, is `## Claims`: the root claim,
  the counts per kind, a line per constant and the line
  `Re-check offline: caterva verify DIR`.
- **One request the search does not make.** After the search, `--claims`
  fetches BRENDA's literature page for each cited reference, one request per
  reference, so that `caterva why` can name the paper. A page it cannot
  fetch does not fail the run: the `## Claims` section says which reference
  and why, and `caterva why` then names the reference id, not the paper.
- **A claim's id is its derivation.** The rule that produced it, with its
  version and the decision record behind it; what it consumed; the spans it
  certifies; and, for a cited or chosen value, the value itself. A
  recomputed value is not in its id: a tolerance is, so a re-integration
  within the tolerance is the same claim. Changing any of that changes the
  id, and a stored id that does not match its contents is caught.
- **Snapshots are dated records, never a cache.** Each carries the day it
  was retrieved, beside its id. No later search reads one.
- **When nothing is written.** A description that builds nothing
  (`Not built.`, exit 3) writes nothing under the directory, and a directory
  that existed is left as it was. Once a model is built, a bundle is written even
  if the search or the export then refuses. `--claims` naming a file is
  refused before anything runs (exit 2). Without `--claims` nothing changes.
- **Exports carry the ids** when you pass both flags: `--export csv` gains
  a final `claim_id` column, the SBML's parameter and species notes gain a
  `CLAIM` line, the Antimony a `# claim:` comment on each assignment, and
  `--export methods` a closing paragraph naming each quantity's claim.
  Without `--claims` the exports are what
  they were: for the model the tests use, the four writers' output was
  compared by hand on 2026-10-24 with what the `v0.5.1-rc.2` tree writes,
  and is byte for byte the same.

## Why a number: `caterva why`

```
caterva why claim:sha256:<hex> --bundle ./claims
```

prints the claim, each rule with its decision record, the evidence ordinals
of the chosen row and its alternatives, each certified span and the text at
it, the row's fields, the snapshot's URL, date, hash and licence, and, when
the bundle holds BRENDA's literature page for the row's reference, the
paper's authors, year, journal, title and PubMed id read from that page.
For the model's root claim it prints every input the same way. A ref that
is not in the bundle is refused (exit 3). `--store DIR` reads the store a
run keeps in the bundle's `store/` folder instead, and writes nothing to it;
a directory that is not a bundle or not a store exits 2 and says why.

## Re-check offline: `caterva verify`

```
caterva verify ./claims
caterva verify ./claims --json
```

- **What it checks.** Every pinned page inflates to at most 64 MiB and
  hashes to its id; a small file that inflates further is refused without
  being read further. Every row and claim id recomputes from its stored
  fields. Every cited claim's row and page are in the bundle, the row's
  reference id, value, substrate, organism and commentary are whole cells of
  one table row of that page, and the claim's value and unit are the row's.
  Every certified span lies inside its page and reads as its text, and a
  cited claim's spans lie inside the one table row that holds the row it
  cites and certify its reference, value and commentary: a claim cannot
  carry another row's bytes and pass. The chosen row is not dominated by an
  alternative, when the ordinals were carried. A stated unit factor
  multiplies out, within the claim's tolerance. Every computed claim's
  inputs exist, and the root claim is computed.
- **Three states, each printed as itself.** `ok` a check held, `FAIL` it
  did not, `n/a` it did not run, with the reason (a dominance check on a
  claim that carried no ordinals). A check that could not run is never
  reported as passed: it is printed `n/a`, counted under "did not run", and
  has `"status": "not run"` in `--json`. The summary counts them apart; on
  the showcase bundle it reads `18 checks: 18 ok, 0 failed, 0 did not run;
  2 not checked. Re-checkable: every check that ran holds against the
  pinned bytes; what did not run is listed above with the reason.`
- **Exit codes.** 0 when no check failed (an `n/a` does not fail the
  bundle), 3 when one failed (stderr names the first failing check and its
  claim), 2 for a directory that is not a bundle it can read.
- **What it says it did not check.** Regenerating the Antimony and replaying
  the integration are listed as not checked, with the reason.
- **What it cannot tell you.** Whether the biology is right. It checks
  derivations and stated reasons against pinned bytes. The word is
  re-checkable.
- **Its own imports are the standard library.** `caterva/check/` imports
  nothing of the code that wrote the bundle, and a guard reads its imports
  on every build. Like every `caterva` subcommand it starts the `caterva`
  package; it loads nothing of the composer or the evidence layer.

## In Caterva Studio: each number's derivation, and a re-check

Every compose run in the Studio writes its claims bundle beside its files,
the one `--claims DIR` writes, and offers it as two downloads
(`claims.zip`, `claims.json`). Activating a number on the Compose screen
now shows, under its citation and conditions, the claim as the bundle
holds it: the claim id (with a button that copies it; it is what `caterva
why` takes), the rule with its decision record, the row's locator and
words, the pinned page's address, date, licence and digest, the paper's
title and PubMed id when the bundle holds BRENDA's literature page for the
reference, and the certified texts. "Re-check this run" runs the checker
`caterva verify` runs over the run's bundle and lists its report; a check
that did not hold is shown first, in the checker's words, naming the
claim. The server's side is `POST /api/runs/{id}/verify`
(`docs/studio/CONTRACT.md`, sections 7, 9, 11, 13, 17 and 18); the guide is
`docs/studio/USING_STUDIO.md`, "Where a number came from, down to the
bytes" and "Re-check a run".

## In Caterva Studio: Rates, from your own measurements

- **Bring a table.** Drop a CSV, TSV or text file on the Rates screen,
  choose one, or paste the cells from a spreadsheet; Home and the command
  palette offer "Fit my data", and R's `datasets::Puromycin` opens as an
  example. A table is limited to 524,288 bytes and 2,000 rows.
- **It says how it read it.** The delimiter, the header, a decimal comma, a
  byte-order mark, Windows line endings, units in headers such as
  `[S] (mM)`, and long, wide and two-column layouts. Every decision is a
  sentence, every problem is located by line and column, and a bad row is
  skipped only in the open, never repaired. A unit is never assumed.
- **It fits as `caterva rates` does.** A figure (rates with error bars, the
  fitted curve with its band, the residuals beneath), the constants each
  marked as fitted from your data with a profile-likelihood interval, the
  lack-of-fit test, the rate laws compared with AICc, the comparison
  between groups and with BRENDA, and what to change when the data cannot
  bound a constant. The error bar comes from your sigma column, your
  replicates or the residuals, and the screen says what each assumes.
- **What you take away.** The figure as SVG and as a 300 dpi PNG for a
  single or double column, the tables as CSV (a text cell a spreadsheet
  would run as a formula is made inert), a methods paragraph generated from
  the run, a citation line and the run's bundle.
- **What is weak.** It has been run on R's Puromycin data and formats of
  its values, not on a laboratory's own tables; the band is pointwise, not
  for the whole curve at once; a table with groups and an inhibitor in wide
  layout is not read. `docs/studio/USING_STUDIO.md`, "Fitting your own
  rates", lists the rest.
- `caterva rates` in the terminal prints what it printed: sixteen golden
  outputs on the real Puromycin table are byte for byte the same, with only
  the machine's version strings masked. Two of its crashes are fixed: a
  table with one group of rows, and a substrate-inhibition constant the
  data bound on neither side (it now says no substrate inhibition is
  detectable).

## In Caterva Studio: an assistant, off unless you turn it on

- **What it does.** It describes a mechanism in words (the engine's
  grammar still decides, and shows its reading first), explains a result,
  drafts methods, answers questions about one run and puts the engine's
  ranked measurements in plain words. It reads Rates runs too.
- **What it may not do.** Author a number, set a constant, produce a
  citation or run anything without your click. Every sentence it writes is
  checked against the run's own result (numbers with their units, names, EC
  numbers, citations) before it is shown, and a text with a figure the
  result does not hold is not shown. Its text carries its own mark, `ai`,
  beside the engine's.
- **Off by default.** Nothing is sent, and no payload is built, until you
  switch on the assistant (Settings, Assistant), the feature you want, and,
  the first time you use each feature, agree to what it sends.
- **What it sends, once on.** Per call, a fixed system prompt and the data
  the feature needs as one JSON document: for an explanation, a methods
  draft, a question or the ranked measurements, a bounded digest of the
  run's result (its figures, units, verdict, concerns and where each figure
  came from), plus your question; for "describe it", the sentence you
  typed, the list of mechanism shapes and the enzyme names the finder
  matched. What you typed or chose to start a run (its title, compound
  names) is left out unless you tick "include my data" for that call. File
  paths, the home folder, the user name, e-mail addresses and anything
  shaped like an API key are removed first. Before the first send of each
  feature, and whenever you ask ("Show exactly what will be sent"), the
  page shows the request byte for byte, and that is what is sent.
- **Where it goes.** To the provider you choose (Anthropic, OpenAI, Groq,
  OpenRouter or Mistral), under their terms and retention policy, not
  Caterva's; or to a model on your own computer at a loopback address (such
  as Ollama), and then nothing leaves the machine. Offline mode blocks every
  provider but a local one. The status line reads "Assistant active: sends
  to" the provider whenever data can leave.
- **The key and the record.** In Caterva.app the key is kept in the login
  Keychain and handed to the server over a private pipe; in a browser or
  development run it comes from `CATERVA_ASSISTANT_KEY`. Every call (the
  provider, the model, the exact payload, the reply, the result of the
  check, the time and your confirmation) is recorded in the run and in
  `assistant/calls.jsonl` in the data folder. `docs/PRIVACY.md` and
  `docs/studio/ASSISTANT.md` say the rest.

## The Mac app

- **It updates itself from 0.5.1.** 0.5.1 was published as release
  candidates (`v0.5.1-rc.1`, `v0.5.1-rc.2`), and either has the updater: it
  offers this version in the app (Caterva menu, Check for Updates) once the
  plain `v0.6.0` release is out, because its feed is the newest release that
  is not a prerelease. The candidate `v0.6.0-rc.1` is offered only with
  Include prereleases on (Settings, Updates). A copy older than 0.5.1 has
  no updater and is replaced by hand from the disk image.
- **Not signed with an Apple Developer ID and not notarised.** The project
  holds no Developer ID. Each update is checked against a key built into the
  app before it installs, which is not an Apple signature. An update from
  one published copy to the next has not yet been watched on a Mac
  (`docs/studio/README.md`, "What was and was not verified").
- **Opening a downloaded copy.** Try to open Caterva from Applications and
  dismiss the message. Then open System Settings, Privacy & Security, scroll
  down to the message about Caterva, click Open Anyway and enter your login
  password. If the window then says the studio server could not start, or
  macOS keeps refusing, open Terminal and run
  `xattr -dr com.apple.quarantine /Applications/Caterva.app`, then open
  Caterva again. If macOS asks when an updated copy first opens, the same
  steps apply. Check the disk image first against its SHA-256 in
  `SHA256SUMS`.
- **Apple silicon, macOS 14 or later**, as in 0.5.0. Your runs and settings
  are in `~/Library/Application Support/Caterva`, and an update does not
  touch them.

## Also in this release

- **A refusal for a missing substrate names the substrates.** When
  `--subject` resolves and the model needs a Km but no `--substrate` was
  given, the refusal names up to eight substrates BRENDA holds Km rows for
  in your organism, most rows first, with the row count for each and how
  many substrates have Km rows there in all, so the re-run is a choice you can
  make. It still never picks one for you, and it reads the enzyme's BRENDA
  page to say so.
- **A language model may propose an EC number, never supply one.** In the
  API server's resolver the model is asked for the enzyme name as stated in
  the query, and for an EC number only if the query text itself contains
  one; a number it returns that is not in the query is dropped and the
  response says so. When the query names no organism the model no longer
  fills one in: the API server's documented default, Homo sapiens, applies
  and is reported in the response as an assumption, as `caterva compose`
  reports the organism its search chose. When both a name and a number
  arrive, the number is used only if the name resolves to it, or to a set of
  enzymes it is one of; otherwise the run is refused as `ec_mismatch`,
  naming both. A name the finder has no answer for leaves the number
  standing, and the log says it was not checked.
- **A shared bundle is read with care.** `caterva verify` reads a pinned
  page a piece at a time and stops at 64 MiB; `caterva why` and the
  Studio's paper view read a literature page in time linear in its length
  (a crafted 310 KB page took 14 s before); `caterva why --store` opens the
  store read-only.
- **A labelled set.** `Tests/fixtures/labelled/` holds the 25 human
  D-glucose Km rows of the recorded hexokinase page, each labelled by hand
  with the isozyme it belongs to and how that was read (the row's words,
  the paper's title, the UniProt accession). It is for scoring a future
  isozyme rule, and its README says what was checked on which date.
- **A placeholder-DOI guard.** No tracked Markdown may print a DOI under an
  example prefix; `docs/ARCHITECTURE_RIGOR.md`, which did, is deleted and
  replaced by `docs/ARCHITECTURE.md`, one present-tense page naming the
  decision record behind each layer.

Nothing about the science changed in the commands that existed in 0.5.1.

## What is not in this release

- **Readings and labels.** A row's interpretation (which isozyme, which
  variant, which condition) is not yet a claim of its own, and the
  resolver's ranking is recorded as its pick, not re-derived; the report's
  "where the evidence did not settle" section is still where the spread is
  shown. That is milestone M3 of the plan. Defeats as data, the persistent
  engine, audits, the ledger and synthesis are M4 and after.
- NCBI, UniProt and PubChem answers the search reads are not pinned; only
  BRENDA's enzyme and literature pages are.
- A bundle can be re-checked for its own consistency, not for who wrote it
  or when: the dates in it are the writer's statements, and it carries no
  signature.

## How this release was cut

As for 0.5.1: the first attempt is a release candidate, `v0.6.0-rc.1`,
which runs the whole pipeline and publishes a pre-release; the plain
`v0.6.0` tag is cut after a candidate has shipped every artifact. The
release stops, and publishes nothing, if the update key (a repository
secret) is missing.

## Install

From the [releases page](https://github.com/math12345678/caterva/releases),
each file listed with its SHA-256 in `SHA256SUMS`:

- `Caterva-0.6.0-macos-arm64.dmg`, the Mac app (Apple silicon, macOS 14 or
  later);
- the app folders, `caterva-0.6.0-linux-x86_64.tar.gz`,
  `caterva-0.6.0-macos-arm64.tar.gz` and `caterva-0.6.0-windows-x86_64.zip`;
- the Python wheel, `caterva-0.6.0-py3-none-any.whl`, and the source
  distribution, `caterva-0.6.0.tar.gz`;
- `Caterva-0.6.0-macos-arm64.zip` and `appcast.xml`, what the app's updater
  downloads and reads (you do not need either to install by hand), and the
  corresponding source of the libSBML the folders carry, of the
  python-libsbml binding and of the two libraries that embed it, with
  `libsbml-copies.tsv`, which lists each copy.

Or clone the repository and run `make setup`.
