# ADR 0034: The committed contract must match what codegen produces

**Status:** Accepted, implemented

**Date:** 2026-08-14

**Relates to:** ADR 0030 (the fix, and a static guard, by a concurrent
agent), ADR 0027 (recorded this drift and understated it), ADR 0015, ADR 0029

## Context

`lib/api-zod/src/generated/api.ts` is the zod schema every HTTP request is
parsed against. It is generated by orval from `openapi.yaml`, it is
committed, and nothing checked either half of that arrangement.

Both halves had failed.

### It did not load

orval's `override.zod.version` defaults to `"auto"`, which inspects the
installed zod — and, per orval's own documentation of the option, *"when no
package metadata is available, `'auto'` now defaults to Zod 4."* zod 3.25
ships a `zod/v4` subpath, detection concluded v4, and orval emitted
`zod.iso.datetime(...)` while still importing from plain `"zod"`, where
`iso` is `undefined`.

So running the repository's own documented command —

```
pnpm --filter @workspace/api-spec run codegen
```

— produced a contract package that **threw on import**. Proven rather than
assumed, by generating and loading one:

```
RESULT: FAILED -> Cannot read properties of undefined (reading 'datetime')
```

The only reason nobody hit it is that the committed files predated the zod
bump and nobody had regenerated.

**ADR 0027 recorded this and understated it.** It called the difference "a
zod/orval version drift that changes validation semantics across the whole
contract" and treated it as a reason to hand-apply a field rather than
regenerate. That was the right call for the wrong reason: the real situation
was not a semantics change, it was a build that did not start.

### It was stale

Separately, the committed files and the regenerated ones disagreed:
`zod.coerce.date()` against `zod.string().datetime({ offset: true })`. Both
valid zod 3, and not the same validator — one coerces a string into a Date,
the other validates a string and leaves it a string. A caller reading
`completedAt` gets a different type depending on which file is in the tree.

## What was already covered, and what was not

This ADR was originally written as if nothing checked the generated
contract. That was wrong, and the correction is the useful part.

**A concurrent agent had already built `scripts/check_generated_client_loads.py`**
(ADR 0030), an hour earlier, doing static checks: is a zod major pinned,
does it match the installed zod, does the generated file contain v4-only
syntax when the installed zod has no `iso`. That is a better first line of
defence than a runtime load, because it names the cause.

So the guard in this ADR was **partly a duplicate**, built by me, in a
session largely spent removing duplicates. Reducing it to the part that is
not covered is the whole of this decision.

### The overlap, measured rather than assumed

ADR 0030 declines a runtime load check on the grounds that
*"`schemas.test.ts` and `physiologicalReferenceRoute.test.ts` already import
`RunSimulationBody`, so a contract that fails to load fails those."*

Half of that is wrong. `schemas.test.ts` does **not** import
`RunSimulationBody` — a deliberately broken contract leaves it at
**41 passed, 0 failed**. Only `physiologicalReferenceRoute.test.ts` imports
it, and with a broken contract that suite does fail: `success: false`,
exit code 1.

**But it reports `numFailedTests: 0`.** The suite fails as a *suite* — zero
tests ran, because the import threw before any test was collected. Anything
reading `numFailedTests` sees no failures. That includes the mutation
harness used throughout this session, and it is the same shape as the
`-qq` problem that blinded `check_no_silent_skips.py`: a real failure
reported in a field nobody was reading.

That is worth writing down independently of this guard.

### What is genuinely unchecked: staleness

Nothing — not ADR 0030's guard, not any test — checks whether the
**committed** generated file still matches what codegen produces.

That gap has already been exercised. **I hand-patched the generated files
twice**, in ADR 0027 and ADR 0028, because a full regeneration would have
swept in an unrelated change. Both times the tree was left in a state where
the committed contract was not the contract codegen would produce, and
nothing could tell.

So this guard keeps one assertion: regenerate into a scratch directory,
compare byte-for-byte with the committed file. The load check stays as a
secondary, because when it fires it names the cause instead of surfacing as
a suite that ran zero tests — but it is **not** the reason this guard exists,
and the ADR no longer claims it is.

## Decision

`scripts/check_codegen_loads.py` regenerates the contract **into a scratch
directory** and asserts two things:

1. the generated module **loads**
2. the committed copy is **byte-identical** to what codegen produces

It never writes under `lib/`. A guard that repairs what it inspects cannot
report, and one that overwrites the contract on the way to failing leaves
the tree worse than it found it.

An earlier version did copy the generated file into `lib/api-zod/src` in
order to import it. That is the shape this guard exists to discourage, and
it demonstrated why within a minute: the cleanup failed on a filesystem
where unlink was not permitted, and the check left litter behind every run.
It now imports from the scratch path with `NODE_PATH` pointed at
`lib/api-zod/node_modules`, so `zod` resolves exactly as it will for the
real package and nothing is written.

### Exit 2 is not exit 0

Missing `npx`, a missing config, orval failing to produce output — all
return **2**, never 0. A codegen check that silently passes when it could
not run is how the broken contract survived in the first place.

## The part worth keeping: the check could not fail

Both branches were mutation-tested. The **staleness** branch fails
correctly — perturbing one line of the committed file produces:

```
The committed contract is not what codegen produces (1 line(s) differ).
  line 192
    committed: createdAt: zod.string(),
    codegen:   createdAt: zod.coerce.date(),
```

The **load** branch could not be made to fail at all.

Three attempts, all of which produced modules that load:

| Mutation | Result |
|---|---|
| `version: 4` | still `zod.coerce.date()` — the `coerce` block removes the `iso` branch |
| `version: 4`, coercion removed | `zod.date()` — loads |
| whole `zod` override removed (`auto`) | loads |

So the branch was **unfalsifiable**: present, plausible, and
indistinguishable from a branch that does nothing. This project's rule is
that a check which cannot fail is worse than no check, because it is
trusted — and that rule applies to the file enforcing it.

Two options were available: delete the branch, or make it provable. Deleting
it would be wrong, because the failure it guards against was real *this
morning* and returns the moment someone bumps zod without re-pinning orval.

So `--selftest` constructs the failure directly: a module using
`zod.iso.datetime`, which is precisely what orval emitted before the pin. It
asserts the load check rejects it, and — the half that is easy to forget —
that the check *accepts* a valid module, so it cannot pass by rejecting
everything.

```
SELFTEST OK: the load check rejects a broken module and accepts a working one.
  rejection detail: Cannot read properties of undefined (reading 'datetime')
```

That error string is the same one a real generated file produced earlier
today. The branch is now falsifiable on demand.

## Consequences

- `scripts/check_codegen_loads.py` is new. It overlaps ADR 0030's guard on
  the load check and is unique on the staleness check.
- `lib/api-spec/orval.probe.config.ts` is new, and **imports the shipped zod
  override from `orval.config.ts` rather than restating it.** A verification
  config with its own copy of the settings verifies the copy — it would go
  on passing while the shipped config drifted, which is the failure mode the
  guard exists to catch, one level up.
- The guard takes roughly two minutes: it runs a real codegen and a real
  module load. It belongs in CI, not in a pre-commit hook.
- `api-client-react` is **not** checked. Its output depends on a second
  toolchain, and the zod schema is the one that gates every request at run
  time. Checking one thing properly beats checking two approximately —
  and naming the unchecked one beats implying both are covered.

## Credit where it is due

The `version: 3` pin in `orval.config.ts` was written by a concurrent agent
working the same tree, with the same diagnosis, reached independently and
about an hour earlier. This ADR covers the guard, not the fix.

That is now twice in this project that two agents have independently found
the same defect within the hour, and both times the defect had the same
shape: something generated, committed, and never executed. It is worth
noticing that the duplication is a signal about where the defects are rather
than about the agents.

## Still open

`allowVariants` (ADR 0029) is **still not exposed over HTTP.** The codegen
path is now clean and guarded, which was the stated blocker — so the
remaining work is `openapi.yaml`, a regeneration, the route, and the cache
key, exactly as `allowCrossSpecies` and `physiologicalReference` were done.
It is named here rather than left implied, because ADR 0029 listed the
blocker and this ADR removed it.


## A process note that cost real time

Two ADR numbers were burned getting here. This content was written as 0030,
which a concurrent agent had already taken; moved to 0031, which another
agent took while the move was in progress; and finally landed at 0034.

`docs/adr/0030-the-generated-contract-is-now-checked.md` and
`docs/adr/0031-the-committed-contract-must-match-codegen.md` are dead files.
This sandbox cannot unlink files on the host mount, so they are emptied with
a pointer rather than removed. **`rm` both** — `check_forbidden_packages.py`
will stay red on Rule 8 until they are gone, and that redness is correct.

The lesson is not "check the number first" — I did, twice. It is that a
number claimed by writing a file is not reserved against agents who cannot
see the write. Nothing here fixes that.
